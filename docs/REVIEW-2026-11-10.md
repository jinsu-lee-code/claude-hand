### 1. Unity 패키지가 MCP for Unity 없이는 컴파일되지 않음

- 확인
  - `ClaudeHand.Editor.asmdef` 5행이 `MCPForUnity.Editor`를 참조함.
  - 빌려 쓰는 형식은 여섯 개: `McpForUnityToolAttribute`, `ToolParameterAttribute`, `ErrorResponse`, `SuccessResponse`, `PendingResponse`, `McpJobStateStore`. 다른 MCP for Unity 형식은 쓰지 않음(패키지 전체를 검색해 확인).
  - 통로가 도구를 찾는 기준도 그 속성임(`ChBridge.cs` 250·260행).
  - 설치 주소가 `…/unity-mcp.git?path=/MCPForUnity#main`(`tools/claude_hand.py` 77행). hand_test의 manifest에도 그대로 들어가 있음.
  - `package.json`의 설명이 아직 "Extra tools for MCP for Unity … Requires MCP for Unity"임.
- 왜 문제인가
  - 결정 6의 목적("MCP for Unity 버전마다 달라질 수 있는 부분에 기대지 않는다")과 어긋남. 호출 경로만 독립이고 컴파일은 묶여 있음.
  - 그쪽에서 이 여섯 중 하나의 이름이나 생성자가 바뀌면 어셈블리 전체가 컴파일되지 않음. 그러면 통로, 채팅창, 되돌리기, 캡처, 현재 상황 보고, 작업 표시줄 알림이 한꺼번에 사라짐.
  - Unity는 git 패키지를 `packages-lock.json`에 커밋 해시로 잠가서 이미 설치한 프로젝트는 당장 바뀌지 않음. 새로 설치하거나 잠금이 풀리는 프로젝트가 그날의 `main`을 받음. 그래서 프로젝트마다 MCP for Unity 버전이 달라질 수 있음.
- 제안
  - 여섯 형식을 패키지 안에 둠(`ChToolAttribute`, `ChParameterAttribute`, 응답 형식, `Library/ClaudeHand/` 아래의 작업 상태 저장). 통로는 결과를 그대로 JSON으로 바꾸므로 형식이 누구 것이든 상관없음. `unity_bridge.py`가 읽는 `_mcp_status`·`_mcp_poll_interval` 필드만 유지하면 됨.
  - asmdef에서 `MCPForUnity.Editor` 참조를 뺌. MCP for Unity에도 도구를 보이고 싶으면 그 패키지가 있을 때만 컴파일되는 얇은 연결 asmdef를 따로 둠(`versionDefines`). 10.3.0 stdio는 어차피 커스텀 도구를 내보내지 않으니(가정 3) 없어도 잃는 것이 없음.
  - `MCP_FOR_UNITY_GIT_URL`을 시험한 버전의 태그로 고정하고, `doctor`가 프로젝트의 잠긴 버전이 시험한 버전과 다르면 알림.
- 확인 안 한 것: MCP for Unity가 실제로 이 형식들의 이름을 바꾼 적이 있는지.

### 2. Claude Hand Tools가 `file:` 절대 경로로 설치됨

- 확인
  - `plan_unity_install`이 `"file:" + package_dir.resolve().as_posix()`를 씀(`tools/claude_hand.py` 1141행).
  - hand_test의 manifest: `"com.claudehand.tools": "file:C:/Users/mbc/Desktop/Unity/claude-hand/unity/com.claudehand.tools"`.
  - 이 PC의 다른 Unity 프로젝트에는 아직 들어가 있지 않음.
- 왜 문제인가
  - 실제 게임 프로젝트에 넣으면 그 프로젝트 저장소의 `Packages/manifest.json`에 이 PC의 절대 경로가 커밋됨. 다른 PC나 빌드 서버에서는 패키지를 찾지 못함.
  - 이 PC에서는 claude-hand 작업 폴더가 열린 프로젝트 전부의 소스가 됨. `git pull`이나 작업 중인 수정이 열려 있는 에디터 전부에서 바로 다시 컴파일되고, 컴파일이 깨진 커밋 하나가 프로젝트 전부를 멈춤.
- 제안
  - 평소 설치는 태그가 붙은 git 주소로 함: `https://github.com/jinsu-lee-code/claude-hand.git?path=/unity/com.claudehand.tools#<태그>`. 8번의 `main`·태그가 먼저 있어야 함. 저장소가 비공개면 Unity가 git 인증을 쓸 수 있어야 함.
  - `file:`은 `unity-install --dev` 같은 개발용 선택으로 남김(hand_test는 이쪽).
  - `selftest`의 "열린 Unity의 `ch_*` 도구가 저장소와 같은가" 검사는 도구 목록 비교에서 버전 비교로 바꿈.

### 3. 가드가 시작도 못 하는 경우에는 통과시킴

- 확인: README의 안전장치 절은 "훅 자체에 문제가 생기면 호출을 막는 쪽으로 동작합니다"라고 함. `run_guard`의 `try`는 입력 읽기와 `guard_decision`만 감쌈(`tools/claude_hand.py` 983~989행). 이 PC에서 경우별로 실행해 본 결과:

  | 경우 | 종료 코드 | 호출 |
  |---|---|---|
  | 입력이 JSON이 아님 | 0, deny 출력 | 막음 (설계대로) |
  | 가드 인자가 잘못됨 | 2 | 막음 |
  | 스크립트 파일이 없음 | 2 (uv가 냄) | 막음 |
  | 파이썬이 시작하다 예외 (문법 오류, import 오류) | 1 | **통과** |
  | 훅 셸이 `uv`를 찾지 못함 (가정 5) | 127 (셸 규칙, 실행해 보지는 않음) | **통과** |

  "통과"의 근거는 Claude Code 훅 문서임: 종료 코드 2만 차단이고, 그 밖의 0이 아닌 코드는 차단하지 않는 오류. 실제 Claude Code에서 그렇게 되는지는 이 PC에서 확인하지 않음.
- 영향
  - 고정의 첫째·둘째 겹(서버 고정, 도구 허용 목록)은 남음.
  - 빠지는 것: `unity_instance`·`set_active_instance` 검사, 대화상자 차단, 작업 중 표시, 되돌리기 지점. 모두 아무 표시 없이 꺼짐. 되돌리기 지점이 안 찍히면 채팅창의 되돌리기 버튼은 예전 지점으로 감.
  - 가드가 2,670줄 파일의 한 명령이라, 그 파일 어디의 오류든 가드를 같이 멈춤.
- 제안
  - 가드를 표준 라이브러리만 쓰는 작은 파일(`tools/guard.py`)로 떼고, 맨 바깥에서 모든 예외를 잡아 deny를 출력함. 진행 보고와 되돌리기 지점은 판단이 끝난 뒤에 하는 지금 순서를 유지.
  - 훅 명령 자체에 셸 수준 안전망을 넣을 수 있는지 봄. Git Bash는 `… || exit 2`로 되지만 PowerShell 5.1에는 `||`가 없음(`hook_command` 주석은 두 셸 모두를 지원한다고 함).
  - `selftest`에 "설치된 하위 세션 정의의 훅 명령을 그대로 실행해서, 다른 프로젝트의 `unity_instance`를 막는지" 확인을 더함.
  - 위가 될 때까지는 README 문구를 실제 동작에 맞춤.

### 4. 핵심 규칙이 지침에만 있고, 지침이 세 곳에 따로 있음

- 확인: 아래 규칙은 코드가 강제하지 않고 감독이 지침을 따를 때만 지켜짐.

  | 규칙 | 적힌 곳 | 어겼을 때 |
  |---|---|---|
  | 채팅창 요청의 답은 `reply`로 | 채널 지침, 감독 스킬 | 채팅창이 답을 받지 못하고 요청이 열린 채로 남음 |
  | 먼저 보내는 짧은 답은 `working: true` | 채널 지침, 감독 스킬 | 그림이 엇갈리고 되돌리기 지점이 둘로 나뉨 (TEST-RESULTS-13이 한계로 적어 둠) |
  | 같은 대상에 하위 세션 둘을 동시에 붙이지 않음 | 감독 스킬, README | 서로 덮어씀 |
  | 같은 `chat_id`는 같은 하위 세션을 이어 씀 | 채널 지침, 감독 스킬 | 창의 대화 맥락이 끊김 (가정 15) |
  | 데스크톱 앱에서 시킨 일도 `origin: desktop`으로 기록 | 채널 지침, 감독 스킬 | 채팅창 기록에서 빠짐 |

  같은 규칙이 채널 지침(영문, `tools/chat_channel.py` 69~92행), 감독 스킬(한국어), 하위 세션 프롬프트에 따로 적혀 있음. 15단계에서 "지침이 채널 설명에만 있어서 감독이 따르지 않음"이 이미 한 번 있었음.
- 제안
  - 답 누락: 채널 서버는 요청이 열려 있는지(`_open_request`)와 마지막 동작 시각(`progress`)을 이미 앎. 동작이 일정 시간 멈췄는데 답이 없는 요청은 서버가 감독에게 채널 알림을 한 번 더 보냄. 실패했을 때만 토큰이 듦.
  - 같은 대상 동시 작업: 가드가 동작을 보고할 때 하위 세션을 구분하는 값을 같이 보내고, 채널 서버가 같은 대상에 다른 값이 일하는 중이면 막게 함. 훅 입력에 그런 값이 오는지부터 확인해야 함.
  - 하위 세션 이어 쓰기: DESIGN이 가정 15의 대안으로 적어 둔 "채널 서버가 agent id를 기억해 메타로 넘긴다"를 함.
  - 지침 중복: 채널 지침에는 태그 형식과 "claude-hand 스킬을 따른다"만 남기거나, 한 원본에서 둘을 만들고 주요 문장이 양쪽에 있는지 테스트로 검사함.

### 5. 창과 담당의 연결을 생성된 `.md`에서 정규식으로 읽음

- 확인
  - `load_agents`가 `~/.claude/agents/*.md`의 훅 명령에서 `--pin \"…\"`과 `--app`을 정규식으로 꺼냄(`tools/chat_channel.py` 156~173행).
  - 이 함수가 불리는 때: 채팅 메시지, 현재 상황 보고(창마다 최대 0.5초에 한 번), 가드의 동작 보고(하위 세션의 도구 호출마다), `reply`, 미리보기, 대화상자 감시(일하는 동안 2초마다). 매번 폴더의 파일을 전부 다시 읽음.
  - `update`의 `parse_generated_agent`는 한 걸음 더 나가서 프롬프트의 한국어 문장에서 경로를 꺼냄: ``파일 `…`, MCP for Blender 포트``, ``(경로: `…`)``(`tools/claude_hand.py` 2064~2076행).
  - 창 정보가 있는 곳이 다섯 군데임: `~/.claude-hand/unity/<hash>.json`(통로), `~/.unity-mcp`(MCP for Unity), Blender 포트 훑기(파일 없음), `~/.claude/agents/*.md`, 채널 서버 메모리.
- 왜 문제인가: 하위 세션 정의 파일이 등록부 노릇까지 함. 훅 명령 형식이나 프롬프트 문장을 고치면 채팅 연결이나 `update`가 오류 없이 어긋남.
- 제안
  - `sync`가 `~/.claude-hand/agents.json`(이름, 앱, 고정 대상, 경로, 서버 키, 메모 경로)을 쓰고 `.md`는 거기서 만든 결과물로 둠. 채널 서버, `update`, `selftest`는 이 파일만 읽고 수정 시각으로 캐시함.
  - Blender 채팅 애드온이 Unity 통로처럼 `~/.claude-hand/blender/<포트>.json`(pid, 포트, 파일 경로, 애드온 버전)을 씀. `sync`와 `doctor`는 포트 10개를 훑고 창마다 Python을 실행하는 대신 이 파일을 읽음. 채팅 애드온이 없는 Blender만 지금 방식으로 찾음.
- 참고: Blender의 고정 대상은 `<파일 이름>@<포트>`라서, 다른 이름으로 저장하거나 포트를 바꾸면 담당 이름과 `chat_id`(채팅 기록 파일 이름)가 바뀜. Unity는 경로 해시라 바뀌지 않음.

### 6. Blender 쪽 로직이 프롬프트 속 코드

- 확인
  - 다른 Blender로 보내기, 받기, Unity로 보내기가 하위 세션 프롬프트의 코드 블록 세 개임(`tools/claude_hand.py` 622~714행의 `BLENDER_PROMPT`). 하위 세션이 이름만 바꿔 `execute_code`로 실행함.
  - `tools/tests/test_blender_recipes.py` 27행이 그 블록을 정규식으로 꺼내 테스트함.
  - 미리보기 캡처도 코드 문자열임(`BLENDER_CAPTURE_CODE`, 910행).
  - 반면 되돌리기는 채팅 애드온의 함수임(`mark_undo_point`, `undo_last_request`). 가드와 하위 세션이 `import claude_hand_chat`으로 부름.
- 왜 문제인가: 하위 세션이 매번 스무 줄 남짓을 옮겨 적어야 하고, 옮기다 달라져도 잡을 곳이 없음. 테스트가 지키는 것은 프롬프트에 적힌 원문이지 실제로 실행되는 코드가 아님.
- 제안

- 이 수정들이 0.9.1이다. `main`에 올렸고, `v0.9.1` 태그는 프로젝트 둘을 나란히 쓰는 확인 뒤에 붙이기로 했다. 그때까지 `unity-install`은 Claude Hand Tools를 폴더 경로로 넣는다.

아직 안 한 것
- 감독 세션과 채팅창이 있어야 보이는 것: 채팅창에서 요청 → 답, 중지 버튼의 화면, 감독이 중지 알림에 답하는 것, `trace`에 실제 요청이 남는 것(TEST-PLAN 22의 B~H, 23의 채팅창 부분). 프로젝트 둘을 나란히 쓸 때의 미리보기(TEST-PLAN 19의 E).
- 요청마다 되돌리기 지점이 찍히는 것은 Claude Hand가 켜져 있을 때만이라, 위 확인에서는 보지 못했다.
- FBX Exporter를 거치는 내보내기는 실행해 보지 않았다(시험 프로젝트에 그 패키지가 없다).

점검 때 "확인하지 않은 것"으로 적은 것 가운데 이번에 확인한 것
- 종료 코드 1·127이면 호출이 통과되는지: 직접 재현하지는 않았다. 대신 실제 Claude Code 2.1.321로 새 훅이 거부를 출력하면 하위 세션의 MCP 호출이 막히는 것은 확인했다.
- PreToolUse 훅 입력에 하위 세션을 구분하는 값이 있는지: 있다(`agent_id`). 하위 세션 정의의 `Stop` 훅도 `SubagentStop`으로 불린다.
- 테스트: Python 232개(3.10, 3.12, 3.14), Blender 5.2.1 안에서 22개. Blender 안 테스트 하나가 일곱 번에 한 번쯤 실패하던 것을 찾아 고쳤다.
